# quantum-ml-reality-check

**Built by AI agents (Claude), directed and reviewed by Athmane Mekhalfia.**

An honest, living answer to one question:

> Where does quantum machine learning (QML) actually stand against strong classical baselines, and
> what is left to do before quantum computers give a real, useful advantage in machine learning?

The repository has three parts:

| Part | What it is |
|---|---|
| [FIELD_MAP.md](FIELD_MAP.md) | The state of the field as nine milestones towards a useful QML advantage. Each has a status, a progress estimate and sources that were opened and read; the brief's own claims were checked and corrected where needed. |
| [RESULTS.md](RESULTS.md) | A reproducible benchmark: simulated quantum models vs tuned classical models on the same real data, with every number generated by the code in this repository. |
| [JOURNAL.md](JOURNAL.md) | A session-by-session log: what was built, verified and failed, and what comes next ([NEXT_SESSION.md](NEXT_SESSION.md)). |

The rules (verified sources only, no invented numbers, tuned baselines, CPU-only, negative results
reported) and the definition of a fair comparison are in [DESIGN.md](DESIGN.md).

## Current headline results

**Benchmark v0 (session 1, 2026-10-12).** Credit-card fraud data (OpenML 1597): 2,000 transactions
per seed at 10 % fraud, 8 features = 8 qubits, 5 seeds, every model tuned on the same
cross-validation folds. Test AUPRC: higher is better, and a random guess scores 0.10.

| Model | Type | AUPRC (mean ± sd over 5 seeds) |
|---|---|---|
| RBF-kernel SVM | classical | 0.918 ± 0.034 |
| Small neural network (MLP) | classical | 0.918 ± 0.027 |
| Gradient-boosted trees | classical | 0.917 ± 0.029 |
| Projected quantum kernel SVM | quantum, simulated | 0.913 ± 0.025 |
| Fidelity quantum kernel SVM | quantum, simulated | 0.911 ± 0.024 |
| Logistic regression | classical | 0.908 ± 0.023 |
| Variational quantum classifier | quantum, simulated | 0.899 ± 0.024 |

**No quantum model beats any classical model.** The gaps are smaller than the seed-to-seed noise, so
under the decision rule fixed in advance (DESIGN.md §6) every quantum-vs-classical pair is "no clear
difference". The leaning goes towards classical: the quantum kernels are ahead of the three strongest
classical models on only 2 of 5 seeds. After tuning, the quantum kernels pick small bandwidths. At those
bandwidths their circuits should be nearly unentangled and behave like smooth classical kernels. That
is our reading of the circuit, not yet a measurement; the next session tests it. Full tables,
timings, a kernel-concentration experiment and the plain-language reading are in
[RESULTS.md](RESULTS.md).

**Field map in one line:** we estimate the field is about **15 %** of the way to a useful quantum
advantage in machine learning. That is about 5 % for classical data, where the careful benchmarks we
reviewed, this one included, find classical models ahead or level. It is about 40 % for learning from
quantum systems, where exponential advantages are proven and have been demonstrated in experiments. See
[FIELD_MAP.md](FIELD_MAP.md).

## What this repository does *not* show

- **No quantum speed-up.** Every quantum model here uses 8 qubits (at most 10) and is simulated
  exactly on an ordinary CPU. A classical computer runs these "quantum" models in seconds, so a result
  here can only say whether these model *designs* are good learners, not whether quantum hardware is
  faster.
- **No hardware.** No shot noise, no gate noise. On real hardware the quantum models would be
  expected to do worse than in this noiseless simulation (FIELD_MAP.md, milestones 6 and 9).
- **One dataset so far,** subsampled to 2,000 rows per seed with 10 % fraud (the real rate is 0.17 %),
  and reduced to 8 features so that it fits on 8 qubits. See DESIGN.md §7 for the full list of
  limitations.

## How to run

Requires Python 3.13 and about 1 GB of disk space for the packages and the cached dataset.

```bash
git clone https://github.com/Athmane-quantum/quantum-ml-reality-check
cd quantum-ml-reality-check
python3.13 -m venv .venv && source .venv/bin/activate
pip install -r requirements-lock.txt && pip install -e . --no-deps

python -m pytest -q                      # unit tests, about 3 minutes
python -m qmlrc.run_all --quick --out-dir /tmp/qmlrc-smoke   # synthetic smoke run, 1-2 minutes
python -m qmlrc.run_all                  # full benchmark: rewrites experiments/*/results.csv and RESULTS.md
python -m qmlrc.run_all --report-only    # rebuild RESULTS.md from the committed CSVs, no computation
python scripts/check_sources.py          # re-check every arXiv ID cited in FIELD_MAP.md
```

The first full run downloads the credit-card fraud dataset from OpenML (about 70 MB, cached in
`data/`, never committed). The full benchmark takes about 8 minutes on a 4-core cloud container with
4 single-core workers (`--jobs 4`, the default); with fewer cores it takes proportionally longer.
`requirements-lock.txt` pins the exact versions used (Linux x86-64).

## Repository layout

```
src/qmlrc/
  data.py         dataset download, subsampling, train/test split, preprocessing
  quantum.py      PennyLane feature map, fidelity and projected quantum kernels
  vqc.py          variational quantum classifier (PennyLane + JAX)
  models.py       every model and its hyperparameter grid (classical and quantum)
  benchmark.py    runs (seed, model) tasks in single-core worker processes
  experiments.py  the experiment definitions that run_all reproduces
  report.py       builds RESULTS.md from the raw CSVs
  run_all.py      python -m qmlrc.run_all
experiments/      raw results (CSV), run metadata, hand-written reading, archived runs
scripts/          check_sources.py + snapshot of cited arXiv titles
tests/            pytest suite (run by GitHub Actions on every push)
```

## How the project continues

Each week an agent session reads the files above, checks recent arXiv papers that could change a
milestone, does the top item of NEXT_SESSION.md with tests, re-runs the benchmark if the code changed,
and appends to the journal. Every change to a status, a progress estimate or a result has to cite a
source or a run.
